# 設計原則リファレンス

Spec-Weaver の設計基盤となる理論と原則。
全スキルから参照される。

---

## 用語定義

本ドキュメントおよび全スキルで使用する用語を定義する。
用語の混同はトレーサビリティの破綻を招くため、厳密に区別すること。

| 用語 | 定義 | 実体 |
|---|---|---|
| **要件** (Requirement) | なぜ作るのか。ビジネス上の必要性 | Doorstop REQ アイテム |
| **仕様** (Specification) | 何を作るのか。システムが満たすべき条件 | Doorstop SPEC アイテム |
| **外部仕様** | 外部のアクターが結果を直接観察できる仕様 | SPEC アイテム (`layer: behavior`) |
| **内部仕様** | システム内部の構造・制約・技術選定に関する仕様 | SPEC アイテム (`layer: architecture`) |
| **振る舞い仕様** | 外部仕様を Gherkin で記述した実行可能なシナリオ集 | `.feature` ファイル |
| **設計文書** | 内部をどう構築するかの記録 | DESIGN / PLAN / ADR ドキュメント |

### 要注意: 「振る舞い」の使い分け

- **「振る舞い仕様」** → `.feature` ファイルのこと。**常にこの意味で使う**。
- **「外部仕様」** → `layer: behavior` の SPEC のこと。「振る舞い仕様」とは呼ばない。
- `.feature` は外部仕様を具体的なシナリオに落としたもの。両者は親子関係にある。

## 原則1: 4層トレーサビリティモデル

仕様は「Why → What → How → Detail」の4層で階層化する。
各層には明確な問い・形式・責任者が存在する。

```
Why    ── REQ（要件）           「なぜ作るのか」
What   ── SPEC（仕様）          「何を作るのか」
How    ── .feature（振る舞い仕様）「外部からどう振る舞うか」
Detail ── DESIGN / PLAN / ADR   「内部をどう構築するか」
```

| 層 | ドキュメント | 問い | ツール |
|---|---|---|---|
| Why | REQ | なぜ作るのか | Doorstop |
| What | SPEC | 何を作るのか | Doorstop |
| How | .feature | 外部からどう振る舞うか | Gherkin |
| Detail | DESIGN / PLAN / ADR | 内部をどう構築するか | Doorstop |

---

## 原則2: ツールの自由度と運用の規約

### ツールは制約を課さない

Spec-Weaver・Doorstop は汎用的な仕様管理基盤であり、ドキュメント階層やリンクの張り方に制約を課さない。

- **ドキュメント階層**: Doorstop のサブドキュメント機能で自由にグルーピングできる
- **アイテム間リンク**: 任意のアイテム間にリンクを張れる（要件↔仕様は1対1とは限らない）
- **機能グループ**: プロジェクトの規模・ドメインに応じて自由に構成できる

### 規約はスキル（運用）で定める

プロジェクト固有のルール（どのレイヤのアイテムをどうグルーピングするか、リンクの推奨パターン等）は、
dev-lifecycle スキルや各プロジェクトの運用規約で定義する。

| 関心事 | ツール側の責務 | 運用側の責務 |
|---|---|---|
| ドキュメント階層 | 自由なサブドキュメント作成を提供 | 推奨グルーピング構造を定義 |
| リンク | 任意のリンクを張る機能を提供 | どのリンクパターンを推奨するか定義 |
| `.feature` との対応 | `@SPEC-xxx` タグで紐づける機能を提供 | 外部仕様には `.feature` を書く規約を定義 |
| 監査 | 整合性の不一致を検出して報告 | 何を不一致とみなすかの基準を定義 |

**Spec-Weaver の役割**: Doorstop と Gherkin のトレーサビリティ・ブリッジ。
層をまたいだ整合性の**可視化**を提供するが、特定の構造を**強制**しない。

## 原則3: 振る舞い仕様（.feature）の適用範囲

振る舞い仕様（.feature）は **外部仕様（`layer: behavior` の SPEC）** に対してのみ記述する。
内部仕様・技術的制約・アーキテクチャ決定は振る舞い仕様の対象外。

### 振る舞い仕様に書くべきもの（外部仕様の検証）

| 例 | 理由 |
|---|---|
| ユーザーがログインすると200が返る | 外部から観察可能な入出力 |
| 無効なトークンでアクセスすると401が返る | エラー時の振る舞い |
| カートに商品を追加すると合計が更新される | 状態変化の観察 |
| 90日以上更新がないアイテムをstaleと検出する | ルールに基づく判定結果 |

### 振る舞い仕様に書くべきでないもの（内部仕様の領域）

| 例 | 理由 | 代替手段 |
|---|---|---|
| データベースのテーブル構造 | 内部実装の詳細 | DESIGN ドキュメント |
| 使用するフレームワークの選定理由 | 技術的決定 | ADR |
| クラス間の依存関係 | 内部構造 | DESIGN + ユニットテスト |
| パフォーマンス要件（レスポンス < 100ms） | 非機能要件 | 内部仕様 + 性能テスト |
| ログ出力フォーマット | 内部観測性 | 内部仕様 + ユニットテスト |

## 原則4: テストの3層分離（Spec-Glue-Execution）

BDD テストは以下の3層に分離する。依存方向は上から下への一方向のみ。

```
 Spec 層 ──── .feature（振る舞い仕様）
    ↓          外部仕様を自然言語のシナリオで宣言
 Glue 層 ──── Step 定義（Python）
    ↓          Spec の翻訳・委譲のみ（ロジック禁止）
 Execution 層 ── ヘルパー / クライアント
                 実際のシステム操作（API呼び出し、DB操作等）
```

| 層 | 責務 | 含めてよいもの | 含めてはいけないもの |
|---|---|---|---|
| **Spec** (.feature) | 外部仕様のシナリオ化 | Given/When/Then、ドメイン用語 | 実装詳細、技術用語 |
| **Glue** (Step定義) | Spec → Execution への翻訳・委譲 | パラメータ受け渡し、assert | if/for、計算、ビジネスロジック |
| **Execution** (ヘルパー) | 実際のシステム操作 | API呼び出し、DB操作、状態管理 | Gherkin の知識、assert |

**依存の方向**: Spec → Glue → Execution（逆方向の依存は禁止）

---

## 原則5: ツールスコープの分別

各ツールには明確なスコープがあり、スコープ外の役割を押し付けてはならない。

| ツール | スコープ | スコープ外 |
|---|---|---|
| **Doorstop** | 要件/仕様のID管理、リンク、バージョン管理 | テスト実行、ドキュメント描画、リンクルール強制 |
| **Gherkin** | 外部仕様の振る舞いシナリオ記述 | 内部設計、非機能要件 |
| **Spec-Weaver** | Doorstop ↔ Gherkin のトレーサビリティ可視化・監査 | テスト実行、仕様作成、構造強制 |
| **behave** | Gherkin シナリオの実行 | 仕様管理、トレーサビリティ |
| **dev-lifecycle スキル** | 開発ワークフローの規約・制約の定義 | ツール機能の提供 |

## `layer` 属性

### 定義

Doorstop SPEC アイテムに付与するカスタム属性。仕様が外部仕様か内部仕様かを明示する。

| 値 | 意味 | 呼称 | 例 |
|---|---|---|---|
| `behavior` | 外部のアクターが結果を直接観察できる | **外部仕様** | API応答、ユーザー操作の結果、ビジネスルール |
| `architecture` | システム内部の構造・制約 | **内部仕様** | データモデル、コンポーネント分割、非機能要件 |

> **注意**: `layer: behavior` の SPEC を「振る舞い仕様」と呼んではならない。
> 「振る舞い仕様」は `.feature` ファイルのみを指す（→ 用語定義を参照）。

### 判断基準フローチャート

```
この仕様は「外部のアクター（ユーザー/API呼び出し元）が
結果を直接観察できるか？」
  │
  ├── はい → layer: behavior（外部仕様）
  │
  └── いいえ ──→「システム内部の構造・制約・技術選定に関するものか？」
                  │
                  ├── はい → layer: architecture（内部仕様）
                  │
                  └── いいえ → 仕様の記述を見直す（どちらにも分類できない場合、
                               仕様が曖昧な可能性がある）
```

### 判断基準3問

1. **外部から観察可能か？** → Yes なら `behavior`（外部仕様）
2. **Given-When-Then で表現できるか？** → Yes なら `behavior`（外部仕様）
3. **ユーザーストーリーの受け入れ条件として書けるか？** → Yes なら `behavior`（外部仕様）

3問とも No なら `architecture`（内部仕様）。

### `testable` と `layer` の関係

| testable | layer | 呼称 | テスト手段 |
|---|---|---|---|
| `true` | `behavior` | 外部仕様 | 振る舞い仕様（.feature シナリオ） |
| `true` | `architecture` | 内部仕様 | ユニットテスト / 統合テスト |
| `false` | `behavior` | 外部仕様（テスト困難） | 手動確認 / VRT |
| `false` | `architecture` | 内部仕様（テスト不要） | レビューのみ |

### YAML での記述

```yaml
active: true
layer: behavior       # ← behavior（外部仕様）または architecture（内部仕様）
testable: true
status: draft
text: |
  （仕様本文）
```

### 段階的導入ルール

- **新規アイテム**: Phase 2（設計）で設定必須
- **既存アイテム**: レビュー時に段階的に付与
- **未設定**: エラーではなく「未分類」として許容（既存ワークフローを壊さない）

## ドキュメント階層の設計指針

### Doorstop のグルーピング

Doorstop のサブドキュメント（子ドキュメント）は、**機能グループ**の表現に使う。

```
REQ（要件ルート）
├── AUTH（認証関連の要件）
├── CORE（コア機能の要件）
└── ...

SPEC（仕様ルート）
├── AUTH（認証関連の仕様）
├── CORE（コア機能の仕様）
└── ...
```

### リンクの自由度

アイテム間のリンクに制約はない。要件と仕様は多対多の関係になりうる。

```
REQ-001 ──→ SPEC-001
         ╲→ SPEC-003
REQ-002 ──→ SPEC-001
         ╲→ SPEC-002
```

ただし、運用規約（dev-lifecycle スキル）で推奨パターンを定めることができる。
